## Upgrade

1. Install the new versions together:

   ```bash
   npm install seroval@^1.9.0 seroval-plugins@latest @seroval/transport@latest
   ```

2. Import the validators from `seroval/validator`. See [The `v` export is removed](#the-v-export-is-removed).
3. Replace checks on error messages with checks on `code`. See [Errors have codes](#errors-have-codes).
4. Replace `cause instanceof RangeError` after an oversized buffer. See [Oversized buffers](#oversized-buffers).

## Breaking changes

### The `v` export is removed

`seroval`, `seroval/read`, `seroval/write` and `seroval/shared` no longer export `v`. The validators are only in `seroval/validator`.

Before:

```js
import { v } from 'seroval';
```

After:

```js
import * as v from 'seroval/validator';
```

`@seroval/transport` 0.1.3 and earlier read `v` from `seroval/read`. Update it to 0.1.4 or later together with seroval.

### Errors have codes

Every error that seroval throws because of the data now extends `SerovalError`, and has a `code` such as `SRV008`. In 1.8, only the three step wrappers extended `SerovalError`. Existing `instanceof` checks still work.

| | 1.8 | 1.9 |
| --- | --- | --- |
| `name` | `'Error'` | The class name, such as `'SerovalMalformedNodeError'` |
| `code` and `step` | none | A code from [the codes table](../errors.md#codes), and the step that failed |
| Production message | A step or error number, such as `Seroval Error (step: 3)` | The code, the step and a link, such as `Seroval SRV008 (deserialize): https://seroval.vercel.app/docs/errors/SRV008` |
| Development message | A message per error | A message per error, rewritten, and for parse errors the path to the value |

Every message changed, so code that matches message text breaks. Check the code instead:

```js
import { SerovalError, fromJSON } from 'seroval';

try {
  fromJSON(body);
} catch (error) {
  if (error instanceof SerovalError && error.code === 'SRV010') {
    // The depth limit was reached.
  }
}
```

[Errors](../errors.md) describes the fields and the production format.

### Oversized buffers

A buffer larger than `maxBase64Length` still throws a `SerovalDeserializationError`. Its `cause` was a `RangeError` and is now a `SerovalBase64LimitError` with the code `SRV020`.

Before:

```js
if (error.cause instanceof RangeError) {
  // The buffer was too large.
}
```

After:

```js
if (error.code === 'SRV020') {
  // The buffer was too large.
}
```

An invalid `maxBase64Length` option is still a `RangeError`, now with the code `SRV019`.

### seroval-plugins

Two errors in `seroval-plugins` were plain `Error` objects and now have codes:

- A value shared between two plugin values throws `SerovalPluginValidationError` ([SRV013](../errors/SRV013.md)), with the plugin `tag` and the `field`.
- Decoding the node of the `AbortController` factory directly throws `SerovalMalformedNodeError` ([SRV008](../errors/SRV008.md)).

The `code` field needs seroval 1.9. With seroval 1.8, the same errors are thrown without a code.
